# 本地上下文 · 界面设计契约

> 冻结于 2026-10-01。**改这个文件要先改 `Theme.swift`，不能反过来。**
> 任何视图里出现写死的颜色、间距、圆角、字号，都是 bug ——
> 那意味着这个应用会慢慢长成五种风格。

目标：让这个应用看起来**像苹果自己出的**，而不是像套了壳的网页。

## 一、为什么上一版丑（具体到每一条）

| 丑在哪 | 错的做法 | 对的做法 |
|---|---|---|
| 结构不是 macOS 的 | 窗口顶部一个居中 segmented 控件切换板块 | **`NavigationSplitView` 侧边栏**，系统自带半透明材质和选中态 |
| 没有材质层次 | 所有面板都是 `Color(nsColor: .controlBackgroundColor)` 平灰块 | `.background.secondary` 卡片 + `.regularMaterial` 面板 |

| 间距随手写 | 16 / 13 / 11 / 9 混用 | **4pt 栅格**：`Space.xxs…xxl` |
| 用字号造层次 | 标题 `title3.bold()`、正文 `callout`、说明 `caption` 各写各的 | 用**颜色和字重**造层次，字号走系统语义阶 |

| 空状态只有一句话 | "暂无数据" | 图标（淡）→ 标题 → 一句说明 → 动作 |
| 卡片文字过载 | 卡片上写类型名 + 每条理由 + 绿勾 | **卡片一眼可辨，依据点开再看** |
| 数字跳动 | 数字用普通字体，变化时宽度左右跳 | `.monospacedDigit()` + `.contentTransition(.numericText())` |

## 五之二、并行施工中踩出来的坑（**新增，务必先读**）

| 坑 | 症状 | 规矩 |
|---|---|---|
| **盒子套盒子** | `PanelBox` 里再放 `PanelBox` → 材质叠材质、描边叠描边 | HIG 原话："adding nested boxes to define subgroups can make your interface feel busy"。**一个区域只有一层 `PanelBox`。** 子组件自带抬头时，外层不要再包 |
| **`EmptyState` 撑爆面板** | 它带 `maxHeight: .infinity`，放进 `PanelBox` 里会把面板拉到无限高 | `EmptyState` **只用于整片区域**的空状态（主内容区、整页）。**面板内部**的空状态用一行 `captionText()` |
| **`FilterChip` 的两种写法** | 加了显式 init 会抑制 memberwise init | 已同时提供 `FilterChip(text:tint:selected:action:)` 和 `FilterChip(_ text:tint:selected:action:)`，两种都能编译 |
| **`Menu` 的 label 里放 `Button`** | 点击被内层按钮吃掉，菜单打不开 | `Menu` 的 label 用 `Chip`；`FilterChip` 只用在真正需要点击的地方 |
| **`annotation` 不加 overflowResolution** | 图表数值标注被边缘裁掉 | 必须 `.annotation(position:alignment:spacing:overflowResolution:)`（macOS 14+） |
| **`catmullRom` 过冲** | 文件计数不可能为负，曲线却画到零以下 | 离散计数用 `.monotone`，不要 `.cardinal` / `.catmullRom` |
| **`metricValue` 装日期** | 34pt 圆体下 `2026-09-12` 在窄列折行 | 大数字位只给**真正的数量**；日期、路径、状态走 `CaliberRow` 或 `caption` |
| **图片/长文本列宽写死** | 固定数值列合计 ≥216pt 时，左右分栏会把路径挤没 | 表格化的区块**竖排全宽**，不要强行分栏 |

## 五之三、两条被承认的例外（不是违规）

1. **结构尺寸用文件内 `enum` 集中定义。**
   窗口尺寸、栏宽、网格最小列宽、行高上限这类**结构常量**不是视觉变量，
   它们不参与"整个应用长什么样"，只参与"这一块占多大"。
   各文件用 `private enum Metrics`（提炼页）/ `enum Shell`（外壳）/ `MapCol`（地图列宽）集中定义，
   **一个文件一套，注释说明它是唯一该改的地方**。

   但 —— **间距、颜色、圆角、字号必须走 `Theme`**。这两类的区别是：
   前者跟着布局走，后者跟着品牌走。

2. **面板内部的空状态用一行 `captionText()`，不用 `EmptyState`。**
   `EmptyState` 带 `maxHeight: .infinity`，放进面板会撑爆。
   只有**整片区域**（主内容区、整页）的空状态才用 `EmptyState`。

## 六、硬规矩（违反即返工）

1. **不写死颜色、间距、圆角、字号。** 一律走 `Theme.swift`。
2. **类型不在卡片上写名字。** 只用 `TypeBadge`（形状+颜色）。
3. **不打勾。** 结论靠**颜色和文字**表达，不靠勾选标记。
4. **不在视图里自己画面板/徽章。** 用 `PanelBox` / `Chip` / `TypeBadge`。
5. **图表只用 `Charts.swift` 里的。**
6. **数字一律 `.monospacedDigit()`。**
7. **空状态用 `EmptyState`。**
8. **`fraction` / 占比条按"当前看得见的这一批"归一**，不按全库 ——
   全库归一的话，一个 14GB 的视频会把所有 2KB 文档压成一根看不见的线。
9. **不许改 `VaultStore.swift` / `VaultQuery.swift` / `FileTriage.swift` / `ClaimStore.swift` 的公开签名。**
   需要新查询 → 在任务里写清楚，交给 Lead。
10. **每改完必须能 `swift build -c release` 通过 + `--selftest` 三分量清账。**

## 七、验收方式

```bash
cd app
sh scripts_build_app.sh                          # 构建 + 打包
./dist/本地上下文.app/Contents/MacOS/LocalVault --selftest
```

**`--selftest` 的输出是三分量，退出码有三位数含义 —— 别只看「有没有红」：**

```
通过 127 · 跳过 0 · 失败 0         exit 0   自检通过。
通过  66 · 跳过 56 · 失败 0        exit 3   自检未完成：56 项没检查 —— 这不等于通过
通过 125 · 跳过 0 · 失败 2         exit 1   自检未通过：2 项失败。
```

- **`跳过` 不是 `通过`。** 没有索引的环境（全新机器、假 HOME）里，数据类断言无从检查，
  它们进「跳过」并各自说明原因，**不参与「全绿」**。分开的理由：
  **`0` ≠ 「没检查」** —— 一旦合并，一个「App 连库都打不开」的状态看起来会和「一切正常」一样。
- **退出码 `3` 是有意的**：非 0，所以任何「非 0 即失败」的脚本也不会当成通过；
  但它又不同于 `1`，所以「没失败只是没检查完」和「真的失败了」不会混。
- **反证已做**：把同一份代码里的断言改坏 → 前置成立时变红（exit 1）、前置不成立时变 ⊘。
  这才证明是两个通道，而不是一个通道换了个说法。

  ## 八、第二轮踩出来的坑（外观重做 → 独立验证 → 修复）

  ### 8.1 「看起来在断言，其实什么都没测」是一类独立的 bug

  这一轮最值钱的发现不是视觉问题，是**验证力失效**。同一个病出现了三次：

  | 写法 | 为什么恒真 | 怎么改 |
  | --- | --- | --- |
  | `zip(a,b).allSatisfy { $0.score >= $1.score }` | 排序方向对、但 score 恒为 0，`0 >= 0` 永远成立 | 补**取值范围**断言，不能只测方向 |
  | `allSatisfy { $0.hitCount <= 5_000 }` | 标题说"不是相关度分"，可相关度分只可能是 100/120/140/160，全都 ≤5000 | 改成**等式**断言：另查一次原文数一遍，相等才算过 |
  | `check(…, "全部为 0 —— score 列越界了")` | **detail 是失败假设，却在 ✓ 旁边照样打印** | detail 只能写**实测取值**，不能写推测的原因 |

  **规矩**：每条断言必须能回答"把代码改坏成什么样，它会失败"。答不上来就删掉它 ——
  一条恒真的断言比没有断言更坏，因为它让人以为这里被守住了。

  配套做法：**破坏性实验**。改坏代码 → 确认断言变红 → 改回 → 再全绿。
  本轮对 `hitCount` 列漂移、`oneliner` 回流各做了一次，都成功变红。

  ### 8.2 数字的三条铁律（都是实测抓出来的）

  1. **上限不许伪装成事实。** 检索 `limit: 300` 而界面写「命中 300 个」——
     实测 `记忆` 真值 432、`邱懿武` 522。必须写「命中 300+ · 只列出前 300 个」。
     同类：`prefix(14)` 的列表、条陈流的 30 条上限、「最近改动 12 个」的徽章。
  2. **同一个量在同一屏出现两次，必须给口径。** 侧栏「9,563 个文件」vs 圆环「9518 个文件已判断」，
     差 45 = 符号链接。要么统一，要么在近处写明差在哪。
  3. **大数字位只放数量。** `MetricTile(value: "已盘点")` 是错的 —— 日期、路径、状态
     走 `CaliberRow` 或 `caption`。34pt rounded 的位置只给真正的数。

  ### 8.3 Swift Charts 的两个具体坑

  - **分类轴（y 轴）的标签放在 band 顶部，而条形居中，两者差半行**（实测 12.5pt，
    9 行全部一致）。`height: .fixed` 只影响条形不影响标签，去掉它**修不了**这个问题。
    正解：`.chartYAxis(.hidden)` + 把类别名画成 `BarMark` 的**前导标注**（跟着条形居中），
    再用 `.chartPlotStyle { $0.padding(.leading, N) }` 给标注留槽。
  - **体量分布不能用线性刻度。** 实测视频 14.14 GB vs 代码 54 MB，线性下后者占全宽 0.6%
    ≈ 一个点。用 **sqrt**：0 字节仍是 0，不用造假的底，量级差 260 倍时宽度差约 10 倍。
    注意：**刻度只在图表内部做，标注必须显示真实值。**

  ### 8.4 深/浅两态怎么验（不要改用户的系统）

  macOS 26 的外观**只认系统设置** —— `-AppleInterfaceStyle Light` 命令参数和
  `defaults write <bundle-id> AppleInterfaceStyle` **都不生效**（都实测过）。
  而为了截图去改用户系统外观是不可接受的。

  所以 app 支持 `--appearance light|dark`：只改**自己这个进程**的 `NSApp.appearance`，
  用户设置一个字节都不动。这是验收深/浅两态的唯一正确做法。

  ```bash
  ./dist/本地上下文.app/Contents/MacOS/LocalVault --tab 提炼 --appearance light &
  ```

  ### 8.5 一条被承认的例外：`SourceTag` 不用勾形图标

  硬规矩 3「不打勾」指的是**结论**（勾=已批准）。但来源标记也不该用勾，
  因为勾在同一个界面里只能有一个含义。来源改成用**形状**区分：
  `person.crop.circle`（人指定）vs `wand.and.stars`（自动发现）。

  ### 8.6 并行施工时不要动别人的文件

  本轮 5 个 agent 并行改 5 个文件，出现 3 次
  `input file 'X.swift' was modified during the build` —— 这不是错误，是**正常的并发现象**，
  重跑即可。但**判断"我的改动有没有问题"必须在冻结快照上做**，
  否则会把别人的在途错误算到自己头上（本轮 `LocalVaultApp.swift` 和
  `SearchView.swift` 各被误判过一次）。
  
## 八、正文预览（2026-10-02 新增）

详情条从「只有依据」扩成「依据 + 正文」。三条口径必须先读：

### 8.1 正文只从索引取，**不读原文件**

`VaultQuery.bodyDetail(dbPath:id:)` 读 `vault.db` 的 `body`。这不是图省事，是口径：

**索引里没有的，这里也不会凭空出现。** 所以「agent 搜得到的」和「你看得见的」是同一份，
可以当场核对 —— 这是事实，不是承诺。

副作用要接受：索引不覆盖的目录、`node_modules` 这类被跳过的、以及 `denied` 的文件，
预览里也会是空的。**这是对的，不该为它开后门。**

### 8.2 正文为空有**五种**原因，界面必须说出是哪一种

只显示一句「没有正文」是偷懒，等于把上限或策略当成事实。实测分布（2026-10-02）：

| 原因 | 本机个数 | 界面该说 |
| --- | ---: | --- |
| 有正文 | 7,382 | 正常显示 |
| 非文本 / 二进制 | 2,370 | 「可能是二进制、或是文字类但超出单篇提取上限」 |
| 文字类但超限未抽取 | 101 | 同上 |
| `truncated=1` 撞 40 万字符上限 | 18 | **「下面不是全文」** —— 不能说成全篇 |
| `denied=1` 按规则不读 | 16 | 「按规则不读正文，索引里只留了元数据」 |

`truncated` 与 `denied` 必须和 `body` **一起**查回来（`bodyDetail` 就是为此而设）。
单独查 `SELECT body` 的写法一律返工 —— 它没法区分「没有」和「有但不全」。

### 8.3 尺寸与交互

- 高度区间 `Metrics.inspectorMin/Default/Max = 190/340/760`
- **抓手只有顶部那一条**（`inspectorGrip`，12pt 高的独立区域）。
  不能整块 inspector 都可拖 —— 否则在正文里选字会变成拖高度。
- `DragGesture.translation` 是**从按下算起的累计值**。逐帧写 `height - translation`
  会自己叠自己、越拖越飞，必须用 `dragStartHeight` 记住起点。
- 渲染 / 原文用 `.pickerStyle(.segmented)`，和 `ViewModePicker` 同一套做法。
- 「在访达中显示」用 `activateFileViewerSelecting` —— **只揭示，不改动**。

### 8.4 大正文不许铺成一堆 Text

索引用 `maxStoredBodyChars = 400000` 截断，所以正文里**真的有 40 万字符的**。
渲染器必须自己设上限并在末尾如实说明，否则滚动会卡死。


### 8.5 两个上限长得一模一样，必须靠标记分开（实测踩过）

正文有**两层截断**，而两层截断都会让「长度」这个数字变成谎言：

| 层 | 在哪 | 表现 |
| --- | --- | --- |
| 列表层 | `SELECT substr(body,1,4000)` | `body.count` 的上限就是 4000 |
| 存储层 | `maxStoredBodyChars = 400000` | `length(body)` 撞顶时就等于上限本身 |

**实测**：本机 7,428 个有正文的文件里，**3,342 个（45%）在修复前一律显示「有可读正文（4000 字）」** ——
`设计契约.md` 真实 8,808 字报 4000，`merges.txt` 真实 40 万+ 也报 4000。

所以 `VaultFile` 带了两个字段，缺一个就会开始说谎：

- `bodyLength` —— `length(body)`，真实字符数
- `bodyTruncated` —— `truncated=1`，**撞了存储上限**

措辞规则（`FileTriage` 里实现）：
- `bodyTruncated` → 「有可读正文（400000 字以上，索引据此截断）」
- 否则 → 「有可读正文（8808 字）」

⚠️ **反过来的错也要防**：一律加「以上」等于把数字废掉。自检里两条断言一正一反，
就是为了让两种错都变红。

### 8.6 `VaultQuery.cols` 与 `VaultStore.queryFiles` 的 SQL 是重复的

两份列清单各写了一遍，**改一处必须改另一处**。

**实测踩过**：给 `VaultQuery.cols` 加了 `length(body)`，却漏了 `VaultStore.queryFiles`，
于是界面真正走的那条路 `bodyLength` 全是 0 —— 自检第 91 条当场变红。
界面走的是 `VaultStore`，不是 `VaultQuery`。

`length(body)` / `truncated` 必须留在**最后一列**，两边的读取下标都按它定位。

## 九、三栏改版 —— 2026-10-02

### 9.1 三页统一成「列表 + 详情」

| 页 | 布局 |
| --- | --- |
| 提炼 | `[文件列表 flex] [详情栏 min 420 / ideal 520 / **max 760**]` |
| 云盘 | `[文件夹 190–250] [资产区 ≥400] [详情栏 240–360]` |
| 检索库 | `[结果列表 flex] [右栏 440–520]` |

**详情栏必须封顶。** 不封顶时 HSplitView 把多出来的宽度全给它：实测 1728pt 窗口下
详情栏吃掉 1127pt，正文一行过长反而难读，而列表栏只剩 370pt（瀑布流一列）。
封到 760 后列表恢复 3 列。

三页的详情栏共用 **`IndexedPreview`**（`FilePreview.swift`）—— 提炼与检索库都从索引取正文。
**不许各写一套**：`VaultQuery.cols` 与 `VaultStore.queryFiles` 各写一份列清单、
改一份漏一份的教训，见 §8.6。

### 9.2 提炼页：详情栏兼作概览

未选中 → 概览（环形图 + 三条 MetricTile 竖排 + 趋势 + 类型分布）。
选中 → 元数据 + 判断依据 + 正文。

**静止态是概览，不自动选中第一个文件** —— 否则概览永远看不到。
`--pick <片段>` 保留；选不中必须往 stderr 出声，不许静默回落（否则截图会「假通过」）。

### 9.3 签字单元：从「档案单元」改成「两秒单元」

原样：一个可滚列表，**33 个顶层目录 × 4 个按钮 = 132 个按钮**，实测签字 **0 条**。
`qiuyiwu-site/SPEC.md:76` 早就写过：「两秒单元完成率 67%，档案单元 0%」——
**0 条不是没人愿意签，是这个单元设计必然的结果。**

现在：一屏一个目标 + 一句话依据 + 两个按钮 + `已判 X / 33`。
跳过**不写条陈**（不算签字）；撤回是追加，不删历史。
收尾态的数字必须真 —— 不许把 0 说成「完成」。

### 9.4 类型判定的两个真 bug（同一个根因，白天看不出来）

1. **`"im"` 当裸子串匹配** —— `IMG_3188.PNG` 的 `im` 来自 `img`，被判成「通讯记录」。
   而 `.comms` 评分 95，会顶到「值得了解」最前面。实测本机 21 个文件因此误判。
2. **`ext` 两种传法没统一** —— 索引侧带点（`.png`），`URL.pathExtension` 不带点（`PNG`）。
   云盘走后者，于是**所有扩展名判断全部落空**，只剩名字启发式在跑。
   这才是 bug 1 露出水面的直接原因 —— 图片那条根本轮不到。

修法：`ext` 在 `FileTriage.infoKind` **收口处**统一（不在调用方，多一个调用方多一次踩坑）；
短词（< 5 字符）走**词边界**匹配，长词才按子串；扩展名判断**排在名字猜测之前**。

两个教训都是同一条：**短子串和隐式约定都会骗人，收口处要显式。**

### 9.5 断言纪律：一条空断言是自己抓出来的

「图片不会因为名字里有 im 被判成通讯记录」写成 `IMG_3188.PNG == .media` 时，
反证（把 comms 挪回 media 之前）**竟然没有变红** —— 因为 `hasToken` 修好后
它压根不匹配 `im`，这条断言根本测不到顺序。换成 `wechat-export.png` 才守得住。

现在每条断言都做过反证，且**正例必须有**（清空词表也能让反例变绿）。

## 十、「值得读」的定义与多级过滤 —— 2026-10-02

### 10.1 先承认旧机制在做什么

旧的是三档平铺（值得了解 / 待定 / 没用）。**它不是在判断价值，是在过滤垃圾。**

证据（同一条信号在「值得了解」里 vs 全库的命中率）：

| 正面信号 | 全库 | 值得了解 | 区分度 |
| --- | ---: | ---: | ---: |
| 90 天内改动 | 99.8% | 99.9% | **1.00×** |
| 在项目目录里 | 100.0% | 100.0% | **1.00×** |
| 人类命名 | 94.3% | 93.7% | **0.99×** |
| 有可读正文 | 75.2% | 95.6% | 1.27× |

四条正面信号里三条是**常量** —— 它们没在筛选，只是在复述"这不是垃圾"。
所以「值得了解」是**过网后的默认值**：过硬件滤网的 2,829 个里 2,363 个（83.5%）都判它。

代码里还写着「硬信号 / 软信号」两档，但 10 处 `noise.append` **全部**配了对应的
`hardNoise.append` —— 「软噪音与正面信号并存 → 交给人」那个分支**永远走不到**，
是死代码。它的注释还写着「如小于 1KB」，而根本没这个信号。

**结论：一个正面信号如果全库和某一档里命中率一样，它就不配当证据。**

### 10.2 一条有序的梯子（六级）

不再平铺三档，改成**一条有序梯子**。前三级占注意力，后三级不占。

| 级 | 名 | 证据 | 实测规模 |
| --- | --- | --- | ---: |
| 0 | **务必读** | 项目入口文档（区分度 **3.08×**） | 71 |
| 1 | **值得读** | 文档笔记 + 实质正文（**2.30×**） | 547 |
| 2 | **值得扫** | 其余可读文档 | 118 |
| 3 | **待定** | 图片/音视频/设计稿 —— 机器读不懂，**不冒充结论** | 466 |
| 4 | **只检索** | 源码/结构化/配置 —— agent 搜得到，不占你注意力 | 1,654 |
| 5 | **不看** | 垃圾 | 6,985 |

占注意力的从 **2,363 降到 736**（3.2×）。旧机制里「值得了解」有 58% 是源代码、
只有 30% 是文档笔记；现在源码全部落到「只检索」。

### 10.3 被删掉的"证据"

实测区分度 < 1.3× 的，**已从理由里删干净**，不再冒充理由：
正文含第一人称「我」1.23× · 正文含判断/认为/决定 1.26× · 正文长度 1.25× · 正文成段 1.10×。

反直觉但重要：**第一人称和判断词没有区分度** —— `.md` 和源码里到处都是「我」和「决定」。
真正的信号是**位置与角色**，不是**内容措辞**。

### 10.4 三个新信号

- **`inDependency`** —— 依赖目录（node_modules / venv / site-packages / .build …）。
  旧机制漏了 268 个：`isBuildArtifact` 没覆盖 venv/site-packages 这类。
- **`isArchived`** —— 归档件。实测 141 个，其中 2 个（归档目录里的项目台账副本）
  原本和正本一起判「务必读」。
- **`isEntryDoc`** —— 入口文档。**限定可编辑文本文档**：`.pdf` 不算。
  实测事故：`Mac操作说明 完全指南.pdf`（别人的视频教程配套手册，167 MB）
  因为名字含「说明」混进了「务必读」。判的是**角色**（能被继续编辑的项目入口），
  不是它能不能读。

### 10.5 判定顺序（顺序本身是设计）

```
不看 → 待定 → 务必读 → 只检索 → 值得读 / 值得扫
```

「务必读」排在「只检索」**之前** —— 入口文档即使躺在代码目录里也算，
判的是它的角色，不是它装的东西。

### 10.6 数字口径

- 撞了存储上限的正文一律报「N 字以上（索引据此截断）」，**不许把上限说成事实**。
  这条在 `只检索` 分支漏过一次（报 400000），被自检抓回。
- `务必读` 的卡片也要报正文字数。字数单独不构成证据（1.25×），
  但"这个文件有多长"是**事实**，卡片上不显示是信息缺失，不是分级问题。

### 10.7 断言纪律

新增 22 条断言，其中 7 条是**构造出来的端到端梯子**（入口文档→务必读、短笔记→值得扫、
依赖目录里的 md→不看…）。理由是：缺少这段，任何一级退化成"永远为空"都不会被发现，
那和没分级一样。

三条反证全部命中预期（改坏 → 对应断言变红）：入口文档信号失效 3 条红 ·
依赖目录识别失效 1 条红 · 务必读降级 2 条红。
