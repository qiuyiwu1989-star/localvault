# 本地上下文 · macOS 应用

## 三个板块（2026-10-01 重构）

按「主动 / 被动 / 沉淀」拆分，对应产品的三件事：

| 板块 | 性质 | 做什么 |
|---|---|---|
| **提炼** | 主动 | 扫描全部文件 → 判断类型 → 区分没用的和值得了解的 → 结果交给人 |
| **云盘** | 被动 | 一个 Dropbox 式的文件夹，你拖进去的 agent 就读得到（拖拽收集逻辑见 `Sources/LocalVault/FileDrop.swift`，那里记着为什么不能在主线程上等回调） |
| **检索库** | 用法 | **先找东西，再下判断。** 带片段与高亮的检索 + 你的判断 |

`记忆库 → 检索库`（2026-10-01 改名）。理由：这个页面的第一件事是**找东西**，
不是**存东西**。原来叫记忆库，重心落在"沉淀"，于是搜索被埋在页面最下面，
而且只有 substring 匹配 —— 没有片段、没有高亮、没有筛选、没有排序。

### 界面的一条规矩：**卡片一眼可辨，依据点开再看**

第一版把类型名字和每一条理由都铺在卡片上 —— 满屏文字和绿勾，
反而看不出哪个是哪个。现在：

- **类型**只用**图标形状 + 颜色**，不写类型名
- **判断**只用**左边一条色条**（绿/橙/灰），不打勾
- **理由全部收进**右侧下方的详情条 —— 依据必须随手能看到，但不能糊在脸上
- 卡片上只留四样：**图标、文件名、路径、体量条**
- 体量条按**当前这一页**的最大值归一，不按全库 ——
  按全库归一的话，一个 14GB 的视频会把所有 2KB 的文档压成同一根看不见的短线

> 这条规矩同时满足两个要求：**视觉密度低**，和**每一个判断都有据可依**。
> 二者不矛盾 —— 矛盾的是"把依据放在哪个位置"。

### 检索口径（检索库）

| 能力 | 怎么做 |
|---|---|
| 命中片段 | 取出关键词前后各约 70 字，**让你知道为什么命中** |
| 命中位置 | 标成 文件名 / 正文 / 路径 |
| 相关度排序 | 文件名命中 > 正文命中 > 路径命中，再看命中次数 |
| 筛选 | 类型 / 时间 / 顶层目录 |
| **无正文文件也能搜到** | 用「一句话索引」（文件名 + 类型 + 路径）兜底 |

最后一条是关键：本机有 **2,202 个文件没有正文**，原来它们只能靠文件名被找到。

### 分类口径（提炼页）

每个文件判成 **值得了解 / 没用 / 待定** 之一，**每条结论都带理由**。

规矩：
- **类型是一票否决的。** 安装包（`.dmg`/`.zip`）、模型权重（`.safetensors`）、
  可执行文件不含"关于主人的信息"，无论它多新、名字多正常。
- **媒体不给否决权。** 照片里当然有你，只是机器读不懂 → 落"待定"，不冒充结论。
- **配置文件、第三方资产不算"关于你的内容"**（`.conf`、`NOTICE`、`LICENSE`、模型词表）。
- **README 是项目自己的入口文档，不是第三方资产** —— 这条是断言抓出来的 bug。

实测（本机 2026-10-01，9,518 个文件，~500ms）：值得了解 2,335 · 没用 6,758 · 待定 425。

**为什么"没用"这么多**：某个前端项目的 `output/releases/` 下有 2,814 个打包产物文件
（30 个版本目录，占整个索引 29.5%）。`ignoredDirs` 里没有 `releases`。



> 状态：可用 · 2026-10-01
> 形态：原生 SwiftUI，零第三方依赖，**只读**

这个应用是 **`SPEC.md` §4 里那张「签字台」** 的本地实现。

> **两张台**：签字台、仲裁台。**这是人和系统仅有的两个接触点。**
> 签字单元必须小到两秒能判：**一句话、一个窗口、两个按钮**。
> 实测：两秒单元完成率 **67%**，档案单元 **0%**。

前一句话解释了它为什么存在；后一句话决定了它长什么样。

## 一、它做什么

| 页签 | 做什么 |
|---|---|
| **概览** | 索引范围、**口径声明**（跳过了 218 个机器生成目录）、类型分布、上次扫描、地图原文 |

## 二、两个不变量在代码里是硬的

`SPEC.md` 第 1 节是已签字的四条不变量。本应用实现其中两条，且**由数据库强制**，不靠调用方自觉：

| 不变量 | 实现 |
|---|---|
| **I** 机器的断言与人的签字，永远可区分 | `signed_by` + `actor_type` 均 `NOT NULL`；`actor_type='machine'` 时 `authority` 只允许 `L0`，越界写入被拒绝 |
| **II** 历史只增不改 | 表上**没有任何 UPDATE / DELETE**；当前判断是事件流的投影（取每目标最新一条）；撤回 = 追加一条 `撤回` 条陈 |

机器写的东西挂在策略名 `policy:localvault-agent` 下，**不假装是人**。

### 表结构（逐字对 `SPEC.md` §2）

`~/.localvault/claims.db` → `claims` 表：

| 字段 | 说明 |
|---|---|
| `kind` | `event` / `material` / `fact` / `judgment` / `consequence` |
| `source_ref` | 指回矿场或上游条陈 —— **必填** |
| `holder` | 谁的 —— **必填** |
| `signed_by` | 人名或机器策略名 —— **必填，不可为空** |
| `ts` | 时间戳 |
| `target_type` / `target` | 指向索引里的哪一条 |
| `verdict` | 判断态（仅 `judgment` 类有） |
| `actor_type` / `authority` | `human`/`machine` · `L0`/`L1`/`L2` |

**为什么单独一个文件、不写进 `vault.db`**：索引是可重建的派生物，判断不是。
两个文件、两种生命周期，混在一起会在某次 reindex 里把判断一起冲掉。
放在同一个数据目录下，所以仍然只有一套数据。

## 四之二、正文预览（2026-10-02 新增）

详情条下半部分现在会显示**索引里存着的正文**。三条口径：

1. **只从索引读，不读原文件。** 索引里没有的，预览里也不会凭空出现 ——
   所以「agent 搜得到的」和「你看得见的」是同一份，可以当场核对。
2. **正文为空有五种原因**，界面分别说清：有正文 / 二进制 / 文字类超限未抽取 /
   撞 40 万字符上限（`truncated`）/ 按规则不读（`denied`）。只显示一句「没有正文」是偷懒。
3. **两层截断的措辞不能混。** 列表层 4000、存储层 400000，两个数字在上限处都会变成谎言。
   撞了存储上限就报「N 字以上，索引据此截断」。详见 `设计契约.md` §8.5。

## 四之三、分发：.dmg（2026-10-02 新增）

```sh
sh scripts_build_app.sh                       # 编译 + 组装 dist/本地上下文.app
sh scripts_make_dmg.sh                        # → dist/本地上下文-<版本>.dmg
sh scripts_make_dmg.sh --mount-check          # 额外做一次 挂载 → 列内容 → 验签 → 卸载
```

dmg 布局就是 macOS 的老规矩：`本地上下文.app` + 一个指向 `/Applications` 的软链（外加这份说明的副本）。
打包只用系统自带的 `/usr/bin/hdiutil`，不依赖 create-dmg。

**先把这个 dmg 做不到的事说清楚**（实测，2026-10-02）：

| 事实 | 命令 | 输出 |
|---|---|---|
| 签名是 adhoc | `codesign -dvv` | `Signature=adhoc` · `TeamIdentifier=not set` |
| 没有开发者证书 | `security find-identity -v -p codesigning` | `0 valid identities found` |
| Gatekeeper 判定 | `spctl -a -vvv --type execute` | `rejected`（exit 3） |
| 分发就绪检查（Apple 自带，跑在加了隔离属性的副本上） | `syspolicy_check distribution` | `Adhoc Signed App`（Warning）+ `Notary Ticket Missing`（**Fatal**），exit 70 |
| 未公证 | `xcrun stapler validate` | `does not have a ticket stapled to it` |
| 只有 arm64 | `lipo -info` | `architecture: arm64`（Intel Mac 上跑不起来） |

**所以：「双击即可」是假话。** 这个 dmg 能装到别的 Mac，但：

1. 首次打开**必须手动放行**（Gatekeeper 会拦）；
2. ~~目标机器必须先有索引~~ —— **这条已经不再成立**：App 自己会用原生索引器建索引，
   首次运行向导让你选目录，不依赖 Node 也不依赖 CLI。（以前确实是「先跑 CLI 建库再开 App」，
   那是一个 Mac 应用要求用户先装另一个语言的运行时，已废弃。）
3. 只有**想接给 agent 用（MCP）**时才需要 Node —— 那种用户手上一定已经有（`node --version` 自查）。
   CLI 源码随 dmg 的 `CLI/` 一起发，不用再 clone 仓库。

完整的首次运行步骤、两条放行办法、以及**这份说明没验证的部分**，见 **[首次运行.md](首次运行.md)**。以那份为准，这里不重复。

## 七、账号体系：**现在不做，而且不能先做**

有人会自然地想："是不是该上账号？登录之后就能把东西推进来了。"

这个直觉里混了两件不同的事，得拆开：

| | 它解决什么 | 现在缺不缺 |
|---|---|---|
| **账号** | 你是谁、东西归谁（跨设备/多人时才有意义） | **不缺。** 本机模式读本机文件，本来就不需要登录 |
| **存储凭据** | 东西放到哪个 COS bucket | 缺 —— 这才是"接云端"的第一个前置 |
| **脱敏闸门** | 哪些内容**允许**出本机 | **最缺。** 本机某数据源里有上千条身份证号，已永久隔离 |

三条理由，按重要性：

1. **账号会绑死本机模式。** 如果"推进来"以登录为前提，那么在没网、没账号、
   没云端的情况下，这个应用就**不能用** —— 而它最主要的场景恰恰是本机。
   通用软件不能有这种依赖。
2. **账号给的是假的安全感。** 登录 ≠ 数据上云了，更 ≠ 脱敏做过了。
   用户以为自己已经"接上云了"，而实际上什么都没动。
3. **`holder` 已经是租户边界了。** SPEC 的表结构里 `holder` 就是归属字段。
   将来做 SaaS，账号只是 `holder` 的一个**入口**，不是它的**替代**。
   先把 `holder` 定好，账号随时能加；反过来则要改结构。

所以顺序是：**脱敏闸门 → 存储凭据 → 账号**。前两个现在就能做，第三个等跨设备的需求真的出现。

## 八、AI 打标 / 标注 / 清洗放在哪

**不在 App 里做，也不写成"字段"，而是由 agent 写成分成条陈（`claims`）。**

理由：SPEC 不变量 II —— **历史只增不改**。AI 的标注是对内容的一种**判断**，
不是一条事实。它必须：

- 是 **L0（机器提议）**，等人认了才变成 L1
- 可以**被撤回**，且撤回是**追加**一条，不覆盖原来那条
- 带 `source_ref`（依据哪个文件、哪一段）

如果把它写成文件上的一个标签字段，就同时破坏了三条：不可追溯、可覆盖、无签名。

这也是"深度记忆库"和这个应用的正确接法：
**别再造第 6 个记忆系统。** `claims` 是**索引和目录**，指向
qmem / qiu-memory / QMemory 里已经存在的内容，并在上面加**判断**这一层。
P046 的结论就是这个：**"应先接回已有记忆，再考虑扩展服务。"**

  ### 一个真 bug 的来龙去脉（值得记住）

  检索 SQL 用**列号**取计算列，加了一列之后全部错位：

  ```
  hitCount := sqlite3_column_int64(s, 13)   // 13 其实是 score
  score    := sqlite3_column_int64(s, 16)   // 16 越界 → 恒为 0
  oneliner := sqlite3_column_int64(s, 17)   // 17 越界 → 恒为空
  ```

  后果：界面把 `100+40+20` 加权出来的**相关度分**显示成「命中 160 处」，
  读起来像"这个词出现了 160 次"；同时 2,202 个无正文文件的「一句话索引」兜底**从未生效**。

  **不报错，只给错数。** 同一类 bug 在这个函数里出过两次。现在改成按
  `sqlite3_column_name` 查列名，查不到就 `assertionFailure`。
